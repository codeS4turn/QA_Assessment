1. A release is two days away and you have one day of testing time. How do you decide what to test?
I would use a risk-based testing approach to prioritize testing based on business impact, likelihood of failure, and severity of potential defects. First, I would review the requirements, recent code changes, and previously reported defects to identify high-risk areas. I would prioritize critical business workflows such as authentication, wallet funding, delivery creation, payment processing, and courier assignment. I would also focus on areas affected by recent changes and integrations with external services. I would execute smoke, functional, regression, and API tests, focusing on negative scenarios and edge cases. Any critical defects would be reported immediately to the team. Finally, I would document the tested areas, outstanding risks, and provide a clear recommendation on release readiness.
2. How would you test the wallet so a business is never debited twice for one delivery?
I would perform idempotency testing to ensure that repeating the same transaction request does not result in multiple debits. I would submit a delivery payment request with a unique idempotency key and resend the same request multiple times, including rapid duplicate requests. I would also simulate network timeouts, retries, and concurrent requests to verify that the wallet is debited only once. I would validate the wallet balance, transaction history, transaction reference, and API response after each attempt. I would also verify that reusing the same key with a different payload is handled correctly. The expected result is one successful debit per delivery, with duplicate requests returning the original transaction result without creating additional charges.
3. How would you put your automated tests into a CI/CD pipeline?
I would integrate my Playwright automated tests into a CI/CD pipeline using GitHub Actions, Jenkins, or a similar tool. I would configure the pipeline to trigger when developers push code or create pull requests. The pipeline would install dependencies, install the required Playwright browsers, and execute the automated tests. I would organize tests into smoke and regression suites so critical tests run early. If a critical test fails, the pipeline should fail and notify the development team. I would also configure test reports, screenshots, and videos for failed tests as pipeline artifacts. This provides quick feedback, helps identify regressions early, and ensures that only builds that meet the required quality checks proceed to deployment.
